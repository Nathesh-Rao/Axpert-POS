# Currency and tax regime design (design only)

Date: 2026-10-12. Approved by the owner as a DESIGN; no code was written. Implementation is a separate Batch 2b with its own plan and approvals. `PricingService`, `Money`, `Qty` and every golden vector stay untouched. axpert_pos was not touched.

### B1. What exists today (audit)
- Currency: 12 const currencies (`CurrencyRegistry`: INR lakh, USD, EUR, AED, KES, NGN, GHS, ZAR, UGX/RWF/XOF exponent 0, TND exponent 3), symbol always a prefix, no separators/locale fields. `Money(minor, currency)` throws on mixing. `MoneyFormatter` pads to the exponent and groups lakh/thousands; several callers re-derive formatting by hand (`cash_panel`, `payment_controller`, `checkout_service`). `PricingService` takes `TaxConfig` (default `TaxConfig.india`: INR, 'GST', exclusive, slabs 0/5/12/18 never read at runtime); inclusive mode exists and is tested but is unreachable from the UI. Nothing registers `PricingService`/`TaxConfig` in GetX: `CartController` defaults to `const PricingService()`, so the app is hard-wired to INR + GST exclusive.
- `CurrencyRegistry.inr` is the default in `Product`, `CartLine`, `Cart`, `Sale`, `SaleTotals`, `ShiftSummary` `fromJson`, and a literal in seeds. Stored sales/carts/products have only `...Minor` ints, no currency code. "Flat amount ₹" is a hard-coded rupee in `discountTabFlat`. Forex selector (USD/EUR/AED/FC) is a display-only label (KG-006).
- Tax in the UI is always ONE line: Bill Summary "Tax Amount" (`totals_card`), cart line caption "GST 18%", receipt "GST" row and header "Retail tax invoice" (fixed English, KG-137), products "GST" column, price-check "GST x%". Sales ledger, returns, reports, customers, reprint, shift close show no tax. Models: `Product.gst` (Bp, JSON percent), `SaleTotals.taxMinor` (single), `ReceiptDocument.tax` (single). No HSN/SAC, GSTIN, state, place of supply, tax mode or label stored anywhere. Settings hold only store NAME, dark, beep, counter, rate; Settings UI shows only dark + beep (KG-161). Rounding: only `PrototypeRounding` (half-up on exact value at six cart-level points); no per-currency or cash rounding; refunds ignore tax (KG-165). Goldens showing tax/GST: `pos_one_line_light` (+950/1100/1440), `shell_pos_light` (+1100/1280/1700), `shell_pos_dark`, `receipt_light`, `receipt_draft_light`, `reprint_light`, `shell_products_light`, `price_check_light`; nearly all show `₹`. 24 test files reference `TaxConfig`/`CurrencyRegistry`; 10 assert literal "₹", "GST" or "Tax Amount".

### B2. Selected currency and region (no backend)
- Interface `StoreProfileRepository` (`load/save`) + `MockStoreProfileRepository` over `LocalStore` (new storage keys = persistence change, **needs approval**), model `StoreProfile`: `countryCode`, `currencyCode`, `stateCode`, `gstin` (nullable), `taxMode` (exclusive/inclusive), cash-rounding choice. `AppConfig` provides only defaults (`IN`, INR, GST exclusive: identical to today's behaviour) and the `StoreProfile` overrides them. A small `ActiveRegion` controller (permanent) resolves profile -> `Currency` + `TaxConfig` and is what `PricingService` is constructed from (registration change only; `PricingService` internals untouched).
- Formatting: keep `Currency` and `Money` unchanged; add a separate `CurrencyFormatSpec` table keyed by currency code (symbol position, decimal/group separators, grouping) consumed by `MoneyFormatter`; hand-rolled formatters in `cash_panel`/`payment_controller`/`checkout_service` move to it. Per-currency decimals already come from `Currency.exponent`.
- Cash rounding: interface `CashRounding` (increment in minor units + mode, e.g. CHF 0.05, SEK/NOK to whole unit) applied by the payment layer to the final payable AFTER `PricingService`, recorded as an explicit "rounding adjustment" line; never inside `PricingService`.

### B3. `TaxRegime` (plain Dart, no GetX) on top of `PricingService`
`abstract interface class TaxRegime { TaxBreakdown breakdown(PricedCart cart, TaxContext ctx); }`. Inputs: the `ExactTotals.lines` that `PricingService` already produces (per-line net and exact tax after bill discount) plus `TaxContext` (seller state, place of supply, customer tax status/GSTIN, tax mode). Output: `TaxBreakdownLine(code, label, rateBp, amount)`, e.g. India intra-state: CGST + SGST (each half of the rate), inter-state: IGST, with a per-HSN/SAC summary for the invoice; VAT regimes return one line. `PricingService` still rounds the total tax once (golden vectors unchanged); the regime splits THAT rounded tax across components with largest-remainder allocation so components always sum exactly to `totals.tax` (odd minor unit goes to SGST by convention, to be confirmed with an accountant). Default regime = `SingleLineRegime` (today's behaviour), so nothing changes until a store profile selects India GST split.

### B4. Data needs (all "needs approval", none in Batch 2)
Tax rate tables loaded from data (JSON asset via `MockJsonDataSource`, snake_case: country -> slabs -> HSN/SAC mapping), per-product `tax_category` and `hsn_sac` (Product model/JSON/persistence change), store GSTIN/state (StoreProfile), customer GSTIN/state (Customer model change), stored sale snapshot of breakdown lines + currency code (Sale JSON/persistence change). No Drift table beyond `device_context_entries` (ADR-014 gate).

### B5. UI impact (nothing changed now; each item needs your approval vs the React prototype, which has one GST line and no settings for these)
Bill Summary tax row(s) (`totals_card`); cart line caption; receipt totals + receipt header (GSTIN, HSN column, CGST/SGST/IGST rows) and print model `ReceiptDocument`; price check; products table (HSN column?); Settings page/dialog (new rows: currency, region/state, GSTIN, tax mode, cash rounding); "Flat amount ₹" string -> currency symbol; forex card; returns/refund quote (tax split, KG-165); reports (no tax today). With the default regime and INR every one of these must render byte-identical, so goldens stay unchanged until you approve a visual change.

### B6. Tests
New golden vectors (our own fixtures, generated from `PricingService` + regime, NOT from React; PricingService/React vectors untouched): GST intra-state (CGST+SGST) and inter-state (IGST), exclusive and inclusive, 0% slab, odd-paise splits and rounding, multi-slab carts, per-currency exponents 0/2/3, cash rounding. Plus property tests (components sum to `totals.tax`; regime never changes totals). Possibly affected existing tests only if defaults change: the 24 Taxconfig/Currency files and the 10 literal-text files; goldens listed in B1 only if UI changes.

### B7. Split
Batch 2 = infrastructure above. Batch 2b = this design, with its own detailed plan, schema/persistence approvals and UI approvals.

## Added decisions for Batch 2b (owner, 2026-10-12)
- (a) Tax rate-group and HSN/SAC subtotals must ALSO sum exactly to the total tax: allocate with the largest-remainder method per group so that every grouping (by component, by rate group, by HSN/SAC) adds up to `totals.tax`. The convention for an odd minor unit (which component receives it, for example SGST) needs an accountant's confirmation before it is fixed.
- (b) Stored records without a currency code (existing carts, sales, products, held bills in `LocalStore`) load as INR and are never rewritten; a currency code is written only on records created after the feature exists.
