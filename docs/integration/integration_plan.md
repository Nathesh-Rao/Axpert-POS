## 4. Integration plan (small reversible stages, all on `integration`; after each stage: report, ask before committing)
Principle: pos_application keeps its UI, theme tokens, AppShell, routes, widgets, strings, icons and ALL goldens. The data/domain/infrastructure side moves toward axpert conventions behind interfaces. No schema, backend contract or persistence change without a named blocker and your approval. No redesign, no unrelated refactor.

- **Stage 0**: branch `integration` (see section 0).
- **Stage 1 (docs only)**: write `docs/integration/{audit_report,integration_plan,progress,codex_workflow}.md`; update `pos_application/CLAUDE.md` (workflow section, integration rules). Nothing else.
- **Stage 2 (pure Dart, no packages)**: port `Result<T>`/`AppFailure` family, `DataSource<T>` + `MockJsonDataSource`, `AppConfig`, `UuidGenerator` + their unit tests (adapted to our lints) into `lib/core/...`. Unused by features yet. Checks: format, analyze, new tests.
- **Stage 3 (money compatibility, needs D1)**: no replacement. Add a cross-check test that runs axpert's `CartTotalsCalculator` rules (per-line half-up, exclusive/inclusive) against our `PricingService` on the same inputs (no discounts, scale<=3) and reports any difference. If identical: document the mapping Money/Quantity -> Money/Qty and the scale<=3 limit; golden vectors untouched. If a difference exists: stop and ask.
- **Stage 4 (packages, one approval at a time)**: (a) `dio` -> `ApiClient`/`DioApiClient` + their tests (injected adapter, no network). (b) `drift`, `drift_dev`, `build_runner` (dev), `path`, `path_provider` (conditional-import isolated) -> `DatabaseProvider` native/web, `axpert_database` with the single `device_context_entries` table at schema v2 as is, `DeviceContextService`, web assets copied (hash-checked) -> tests with in-memory DB. Verify: a release web build still loads (WASM, headers) and `flutter test` works with the sqlite3 hook. Generated `.g.dart` committed as axpert does. No operational tables.
- **Stage 5 (wiring, no UI)**: extend `InitialBinding` (idempotent) with AppConfig, ApiClient, DatabaseProvider, DeviceContextService, UuidGenerator, auth/session interfaces (unconfigured), lifecycle observer; bootstrap opens DB before `runApp`. No duplicate registrations, no GetMaterialApp change, no second router. Route test + semantics guard + debug click-through (both modes) must stay clean.
- **Stage 6 (pilot feature, needs D2-D4)**: Products (read-only table, smallest) re-laid-out as domain/data/presentation: domain `ProductRepository` returning `Result`, `ProductsMockDataSource` (JSON asset via `MockJsonDataSource`, DTO -> entity), existing mock repository logic kept behind it; views/widgets untouched. Goldens must not change. Then Customers, then others one per stage, only after the pilot is accepted.
- **Stage 7 (checkout side)**: introduce `PaymentService` interface (+mock) for the existing checkout flow, and optional `saleId` (UUID) on new sales; keep our `PricingService` as the single totals engine; use cases only where they add a seam. Existing behaviour and 949 tests preserved.
- **Stage 8 (final)**: full VM suite, goldens, debug click-through both modes, release web_check at 950x733 / 1280x720 / 1868x1035, macOS debug launch, Windows not buildable here (stated), `final_report.md`, confirm axpert_pos unmodified, active branch `integration`, list changed files.
